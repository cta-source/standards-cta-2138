Abstract

This document enumerates technologies that should not be used in connected devices either because they are formally Deprecated by Acknowledged Authorities; or because they are broadly considered insecure but have not been formally Deprecated by an Acknowledged Authority.

This standard was developed by the Consumer Technology Association’s R14 Cybersecurity and Privacy Management Committee. This is an approved and published CTA standard document. All CTA standards are available at CTA.tech/Standards.

1. Scope

This document enumerates two groups of technologies that should not be used in connected devices for security reasons.

The first group of technologies are those that are formally Deprecated by Acknowledged Authorities.

The second group of technologies are those that are broadly considered insecure but have not been formally Deprecated by an Acknowledged Authority. This may be, for example, because there is no Acknowledged Authority that can claim ownership, or for some other reason that prevents qualifying for the Formally Deprecated Technologies list (section 4).

In some cases, the addition of additional security measures, such as an appropriate version of Transport Layer Security (TLS), may be considered appropriate security for the application. For example, FTP may be combined with TLS as FTPS (FTP-SSL). However, whether this approach meets applicable security requirements is outside the scope of this document.

3. Definitions

Acknowledged Authority: The technology owner or standards development organization, a recognized government agency with the appropriate scope and expertise, or a significant private sector entity that has been responsible for broad deployment of the technology.

Deprecation: A strong statement discouraging usage in favor of alternatives.

Prohibited by Process Owner: Indication that certification body, customer, or platform does not permit use of the technology to connect to their system or within the products they certify.

Withdrawn: Indication that the body which initially issued the standard or endorsed or approved the technology has withdrawn (or revoked) such standard or ended such approval.

4. Formally Deprecated Technologies

These technologies are formally Deprecated by Acknowledged Authorities.

4.1 DES (Data Encryption Standard)

Status: Withdrawn

Authority: NIST

Statement:

“…the DES is being withdrawn because it no longer provides the security that is needed to protect federal government information.”

Reference: National Institute of Standards and Technology, NIST Withdraws Outdated Data Encryption Standard, June 2005. http://www.nist.gov/itl/fips/060205_des.cfm.

4.2 DTLS 1.0 (Datagram Transport Layer Security Version 1.0)

Status: Obsolete; replaced by DTLS 1.2; do not fall back to DTLS 1.0.

Authority: IETF Best Current Practice

Statement:

“This document updates the following RFCs that normatively reference TLS 1.0, TLS 1.1, or DTLS 1.0. The update is to obsolete usage of these older versions.

“…The update is to obsolete usage of these older versions. Fallback to these versions is prohibited through this update. Specific references to mandatory minimum protocol versions of TLS 1.0 or TLS 1.1 are replaced by TLS 1.2, and references to minimum protocol version DTLS 1.0 are replaced by DTLS 1.2.”

Reference: IETF RFC 7525, Recommendations for Secure Use of Transport Layer Security (TLS) and Datagram Transport Layer Security (DTLS), https://www.rfc-editor.org/rfc/rfc7525.txt, January 2024.

4.3 Dual_EC_DRBG_(Dual Elliptic Curve Deterministic Random Bit Generator)

Status: Withdrawn

Authority: NIST

Statement:

“Based on its own evaluation, and in response to the lack of public confidence in the algorithm, NIST removed Dual_EC_DRBG from the Rev. 1 document.”

Reference: National Institute of Standards and Technology, NIST Removes Cryptography Algorithm from Random Number Generator Recommendations. April 2014. http://www.nist.gov/itl/csd/sp800-90-042114.cfm.

4.4 MD5

Status: Deprecated

Authority: CERT

Statement:

“Do not use the MD5 algorithm. Software developers, Certification Authorities, website owners, and users should avoid using the MD5 algorithm in any capacity. As previous research has demonstrated, it should be considered cryptographically broken and unsuitable for further use.”

Reference: CERT Coordination Center, MD5 vulnerable to collision attacks, http://www.kb.cert.org/vuls/id/836068, January 2009.

4.5 RC4 (Rivest Cipher 4)

Status: Deprecated (“prohibited”) for TLS/SSL

Authority: IETF Standards Track RFC

Statement:

“Prohibiting RC4 Cipher Suites: This document requires that TLS ([RFC5246] [RFC4346] [RFC2246]) clients and servers never negotiate the use of RC4 cipher suites.”

Reference: IETF RFC 7465, Prohibiting RC4 Cipher Suites, https://www.rfc-editor.org/rfc/rfc7465.txt.

4.6 SHA-1 (Secure Hash Algorithm 1)

Status: Prohibited for use in digital signatures / Deprecated for other uses

Authority: NIST

Statement:

“[SHA-1 for signature generation] [d]isallowed, except where specifically allowed by NIST protocol-specific guidance.”

Reference: National Institute of Standards and Technology. NIST Transitioning Away from SHA-1 for All Applications. December 15, 2022. https://csrc.nist.gov/news/2022/nist-transitioning-away-from-sha-1-for-all-apps.

National Institute of Standards and Technology. Transitioning the Use of Cryptographic Algorithms and Key Lengths. NIST SP 800-131Ar2. Gaithersburg, MD: National Institute of Standards and Technology, March 2019, p18. https://doi.org/10.6028/NIST.SP.800-131Ar2. 

4.6.1 Additional Authorities

This subsection provides additional context.

Status: Deprecated for use in newly generated X.509 certificates within the Microsoft root Certificate Authority program; see statement and reference below.

Authority: Microsoft

Statement:

“The new policy will no longer allow root certificate authorities to issue X.509 certificates using the SHA-1 hashing algorithm for the purposes of SSL and code signing after January 1, 2016.”

Reference: Deprecation of SHA-1 Hashing Algorithm for Microsoft Root Certificate Program, https://technet.microsoft.com/library/security/2880823, November 2013.


Status: Deprecated for Chromium handling of TLS certificates; see statement and reference below.

Authority: Google

Statement:

“The use of SHA-1 within TLS certificates is no longer sufficiently secure. This is an intent to phase them out (in 2-3 years).”

Reference: Intent to Deprecate: SHA-1 certificates, https://groups.google.com/a/chromium.org/forum/#!msg/security-dev/2-R4XziFc7A/NDI8cOwMGRQJ, August 2014.


Status: Deprecated for use in certificates seeking to connect to Facebook; see statement and reference below.

Authority: Facebook

Statement:

“…apps that don't support SHA-2 certificate signatures will no longer be able to connect to Facebook starting on October 1, 2015.”

Reference: Moving to a More Secure Standard: Please Update your Apps To Support Certificates Signed with SHA-2, https://developers.facebook.com/blog/post/2015/06/02/SHA-2-Updates-Needed/?_fb_noscript=1, June 2015.

4.7 SSL 2.0 (Secure Sockets Layer Version 2.0)

Status: Deprecated (“prohibited”).

Authority: IETF Standards Track RFC

Statement:

“Prohibiting Secure Sockets Layer (SSL) Version 2.0: This document requires that when Transport Layer Security (TLS) clients and servers establish connections, they never negotiate the use of Secure Sockets Layer (SSL) version 2.0.”

Reference: IETF RFC 6176, Prohibiting Secure Sockets Layer (SSL) Version 2.0, https://tools.ietf.org/html/rfc6176, March 2011.

4.8 SSL 3.0 (Secure Sockets Layer Version 3.0)

Status: Deprecated.

Authority: IETF Proposed Standard

Statement:

“Deprecating Secure Sockets Layer Version 3.0: The Secure Sockets Layer version 3.0 (SSLv3), as specified in RFC 6101, is not sufficiently secure. This document requires that SSLv3 not be used.”

Reference: IETF RFC 7568, https://tools.ietf.org/html/rfc7568, June 2015.

4.9 TLS 1.0 and TLS 1.1 (Transport Layer Security Versions 1.0 and 1.1)

Status: Deprecated

Authority: IETF Best Current Practice

Statement:

“This document formally deprecates Transport Layer Security (TLS) versions 1.0 (RFC 2246) and 1.1 (RFC 4346). Accordingly, those documents have been moved to Historic status. These versions lack support for current and recommended cryptographic algorithms and mechanisms, and various government and industry profiles of applications using TLS now mandate avoiding these old TLS versions.

“…The update is to obsolete usage of these older versions. Fallback to these versions is prohibited through this update. Specific references to mandatory minimum protocol versions of TLS 1.0 or TLS 1.1 are replaced by TLS 1.2, and references to minimum protocol version DTLS 1.0 are replaced by DTLS 1.2.”

Reference: IETF RFC 7525, Deprecating Secure Sockets Layer Version 3.0, https://www.rfc-editor.org/rfc/rfc7525.txt, January 2024.

4.10 Triple Data Encryption Algorithm (TDEA)

Status: Withdrawn

Authority: NIST

Statement:

“The scheduled withdrawal of SP 800-67 Rev. 2 will signify that TDEA is no longer an approved block cipher.”

Reference: National Institute of Standards and Technology. NIST to Withdraw Special Publication 800-67 Revision 2 | CSRC; June 29, 2023. https://csrc.nist.gov/news/2023/nist-to-withdraw-sp-800-67-rev-2. Notice of the withdrawal going into effect is available at https://doi.org/10.6028/NIST.SP.800-67r2.

4.11 WEP (Wired Equivalent Privacy)

Status: Deprecated

Authority: IEEE

Statement:

“This amendment retains the WEP feature for purposes of backwards compatibility with existing IEEE 802.11 devices, but WEP is deprecated in favor of the new security features provided in this amendment.”

Reference: IEEE 802.11i-2004, Amendment 6 to IEEE Std 802.11-1999; https://standards.ieee.org/ieee/802.11i/3127/.

Status: Deprecated

Authority: Wi-Fi Alliance

Statement:

“TKIP is an older security technology with known vulnerabilities to some cryptographic attacks. TKIP and WEP use the same underlying cipher, and, consequently, they are vulnerable to a number of similar attacks. TKIP was designed as a transitional mechanism in 2004 for devices equipped with WEP and unable to support AES. Due to the known vulnerabilities of TKIP, networks utilizing it may be more susceptible to attack.”

Reference: Wi-Fi Alliance, Technical Note: Removal of TKIP from WiFi Devices, v. 1.0, March 15, 2015. Available at https://www.wi-fi.org/system/files/Wi-Fi_Alliance_Technical_Note_TKIP_v1.0.pdf

4.12 WPA

Status: Deprecated

Authority: Wi-Fi Alliance

Statement:

“WPA, which uses Temporal Key Integrity Protocol (TKIP), no longer provides sufficient security to protect consumer or enterprise Wi-Fi® networks.”

Reference: Wi-Fi Alliance, Technical Note: Removal of TKIP from WiFi Devices, v. 1.0, March 15, 2015. Available at https://www.wi-fi.org/system/files/Wi-Fi_Alliance_Technical_Note_TKIP_v1.0.pdf

4.13 TKIP (Temporal Key Integrity Protocol)

Status: Deprecated

Authority: Wi-Fi Alliance

Statement:

“TKIP is an older security technology with known vulnerabilities to some cryptographic attacks. TKIP and WEP use the same underlying cipher, and, consequently, they are vulnerable to a number of similar attacks.”

Reference: Wi-Fi Alliance, Technical Note: Removal of TKIP from WiFi Devices, v. 1.0, March 15, 2015. Available at https://www.wi-fi.org/system/files/Wi-Fi_Alliance_Technical_Note_TKIP_v1.0.pdf

4.14 Android Beam (NFC API)

Status: Deprecated.

Authority: Google

Statement:

“In Android 10 we're officially deprecating Android Beam, an older feature for initiating data sharing across devices through Near Field Communication (NFC).”

Reference: Android Developers, https://developer.android.com/about/versions/10/behavior-changes-all#beam-deprecation.

4.15  Zebra NDEF (NFC Data Exchange Format)

Status: Deprecated

Authority: Zebra

Statement:

“Note: DEPRECATED; control of this feature by NFC Manager will be discontinued in a future release. Supported only on MC93, TC52, TC57, TC72, TC77 and TC8380 devices.”

Reference: Zebra Tech Docs, https://techdocs.zebra.com/mx/nfcmgr/.

4.16 LDAP (Lightweight Directory Access Protocol) Versions 1 and 2 (LDAPv1, LDAPv2)

Status: LDAPv1 is Obsolete per RFC 1777 and RFC 3494. LDAPv2 is Historic per RFC 3494

Authority: IETF

Statement:

“…LDAPv2 does not provide adequate security features for use on the Internet. LDAPv2 does not provide any mechanism for data integrity or confidentiality. LDAPv2 does not support modern authentication mechanisms such as those based on DIGEST-MD5, Kerberos V, and X.509 public keys.”

“Developers should not implement LDAPv2 per [LDAPv1] RFC 1777, as such would result in an implementation that will not interoperate with existing LDAPv2 implementations. Developers should implement LDAPv3 instead.”

Reference:

IETF RFC 3494, Lightweight Directory Access Protocol version 2 (LDAPv2) to Historic Status, https://www.rfc-editor.org/rfc/rfc3494.html.

IETF RFC 4511, Lightweight Directory Access Protocol (LDAP): The Protocol, https://www.rfc-editor.org/rfc/rfc4511.html.

5. Known Insecure Technologies

The technologies listed in this section are known to be insecure, and therefore should not be used alone, but may be made secure for use with secure extensions, or over a link secured by other means.

An IoT product should not use a technology that is considered insecure (for example, technologies with known Common Vulnerabilities and Exposures or cryptographic algorithms/parameters with known vulnerabilities), and manufacturers should attempt to identify and eliminate such out-of-date or compromised technologies from their product line. In addition, unless compensating controls are applied, an IoT product should not use outdated and potentially insecure protocols such as:

5.1 FTP (File Transfer Protocol)

FTP implements unencrypted data transfers including credentials, does not verify integrity of transferred files, and is vulnerable to man-in-the-middle attacks.

Alternatives include SSH FTP (known as “SFTP” or “Secure FTP”) and FTP over TLS (known as “FTPS”, “FTP-SSL” or “FTP Secure”).

5.2 IRC (Internet Relay Chat)

IRC is a public instant messaging system that implements unencrypted data transfers including credentials.

Alternatives include Matrix and Extensible Messaging and Presence Protocol (XMPP).

5.3 Telnet

Telnet implements unencrypted data transfers including credentials.

Alternatives include Secure Shell (SSH).

5.4 NetBIOS (Network Basic Input/Output System)

NetBIOS may be desirable for an IoT device that should be discoverable by Windows machines. However, NetBIOS has multiple potential vulnerabilities including enumeration, name service spoofing, name query poisoning, and man-in-the-middle attacks.

Alternatives include DNS and SMBv2/v3.
